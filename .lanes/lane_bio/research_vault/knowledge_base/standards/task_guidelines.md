# Scientific Taste: Task Engineering Guidelines

Bad tasks lead to bad execution. Every task in `journal.md` MUST adhere to these standards.

## 1. ATOMIC (Atomicity)
- **Rule**: A task must be completable in a single execution step (one script run, one search).
- **Bad**: "Implement and test the model." (Too big)
- **Good**: 
    - "Implement `SparseAttention` class in `src/model.py`."
    - "Write unit test for `SparseAttention`."
    - "Run `pytest tests/test_attention.py`."

## 2. SPECIFIC (Specificity)
- **Rule**: No ambiguity. Use filenames, variable names, and metric thresholds.
- **Bad**: "Optimize the code."
- **Good**: "Replace `torch.matmul` with `triton.ops.matmul` in `layer.py` to reduce latency."

## 3. VERIFIABLE (Definition of Done)
- **Rule**: Every task must have a binary success criteria.
- **Bad**: "Check if it works."
- **Good**: "Run training loop for 100 steps. Success if Loss < 0.5 and no NaN values."

## 4. CONTEXT-AWARE
- **Rule**: Must specify dependencies.
- **Example**: "Requires `data/processed.pt` generated by Task 1.2."

## 5. EXPERIMENT CONTROL STANDARDS (The Scientist vs Technician Rule)
- **Rule**: Separate **Logic Discovery** from **Parameter Optimization**.
- **The "Scientist Mode" (Code Gen)**: 
    - Use when: Inventing new architectures, changing loss functions, adding new layers of complexity.
    - Action: Modify `.py` files directly (e.g., `exp_{hash}.py`).
    - **Control**: Version Control (Git) is your safety net.
- **The "Technician Mode" (CLI Args)**:
    - Use when: Sweeping learning rates, changing batch sizes, swapping standard baselines.
    - Action: Use `argparse`. Do NOT edit code just to change a constant.
    - **Control**: Command String (logging the full `python train.py ...` command) is your safety net.
