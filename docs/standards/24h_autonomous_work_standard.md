# OpenClaw 24小时无人值守干活与安全作业规范

**状态**: 核心约束红线 (Core Redline)
**生效级别**: P0 (最高)

为了确保机器人在 24/7 全天候运行与后台静默干活期间，不卡死、不把磁盘挤爆、不暴露敏感节点，特确立以下“不可逾越”的红线规范：

## 第一条：绝对“资源与网络隔离” (The Download Standard)

经历了数次在 Mac 02 / 03 上直接拉代码导致的连接阻断与空间占用后，确立终极下载防线：

- **严禁在算力节点直连外网**：严禁让 Mac 02 (ASR节点)、Mac 03 (核心堡垒) 或 GPU 服务器直接去拉取海外 GitHub 仓库或超大 HuggingFace 模型。
- **出口机专用化 (Proxy Exit Node)**：**所有**涉及翻墙、大网宽吞吐的资源下载，**必须且只能**交由边缘出口节点（如 Windows 跳板机 `roy-005: 100.98.236.51`）执行。
- **统一工具链**：全面强制使用 `skills/claw-fetch` (Aria2 并行拉取) 或 `skills/proxy-downloader`。
- **阅后即焚 (Zero Footprint)**：出口机只做下载中转，下载物一旦转移（SCP）到 `Mac 03` 的 `~/.openclaw_backups` 等核心数据保险箱后，必须在出口机上执行 `del` 或 `rm -f` **彻底物理销毁**，严禁把垃圾遗留在前线出口机。

## 第二条：内存“用完即自杀”原则 (Zero-Footprint Execution)

针对边缘终端（如 Mac 02 的 `whisper.cpp` ASR）和脆弱终端：

- 坚决摒弃“启动一个常驻后台 API 等着人来调用”的旧思想（旧思想导致了常驻环境占用几十GB内存最终崩溃）。
- **按需唤醒 (On-Demand)**：只维护一个极简的调度器。只有在飞书发来语音时，闪电拉起底层 C++ 引擎或 PyTorch 推理，吐出结果后，**必须强制 `exit(0)` 或 `kill` 掉推理进程**，把宝贵的物理内存 100% 吐回给 macOS。

## 第三条：GPU 死锁护甲与防爆 SOP (The OOM Guard)

针对 V2V 和 TTS 等高密算力流：

- 外部输入（音频文件/切片）在碰触 `cuda` 之前，必须被 Python 客户端进行“边界断言”（例如强制切片在 2.0s ~ 8.0s 之间）。绝不允许长音频憋爆显存。
- 所有模型推理代码必须包裹在 `try...except RuntimeError(OOM)` 的防爆服内。
- 不论推理成功还是报错，函数的 `finally` 块中必须包含 `torch.cuda.empty_cache()` 或 `gc.collect()`，实现内分泌自发自愈。

## 第四条：网络暗道的“无常识假设” (Tunnel Resiliency)

不要相信任何长连接能长久存活，尤其在复杂的内网穿透体系中。

- **清理先于重建 (Kill First)**：在构建任何端口映射（SSH / Socat）之前，必须假设旧端口是“僵尸占用”状态。打通前，必须执行 `lsof -t -i:端口 | xargs kill -9` 或 `fuser -k` 进行物理级肃清。
- **防误杀护盾**：严禁执行无脑的 `killall python`，以免拔掉无辜的同行服务。必须通过精准的 PID 管理或 `tmux` 会话来进行生命周期管控。
